# RAG context-order sensitivity audit

Relevant evidence can still produce an unstable answer when its order changes in the
prompt. Models may over-weight early or late chunks, omit a citation after a harmless
permutation, or change from an answer to an abstention even though retrieval returned
the same evidence set. Aggregate retrieval and grounding scores do not reveal this
failure mode.

`src/context_order_audit.py` evaluates pre-recorded generation runs that hold the
query, model, prompt template, retrieval snapshot and generation configuration fixed
while permuting only the order of retrieved chunks.

## Release contract

Each query records one baseline and multiple order variants. Every variant must:

- contain exactly the same unique chunk IDs;
- cite only chunks in that fixed evidence set;
- use the same model, prompt, snapshot and generation configuration identities;
- provide a non-empty answer and citation unless it explicitly abstains;
- omit citations when it abstains.

The audit measures:

- number of unique evidence orders;
- maximum normalized Kendall distance from the baseline order;
- worst citation-set Jaccard similarity to the baseline;
- worst answer-token Jaccard similarity to the baseline;
- number of answer/abstention decision flips.

Default policy requires four distinct variants, meaningful order displacement, at
least `0.80` citation-set stability, at least `0.70` lexical answer stability and no
abstention flip. Thresholds are explicit policy and should be calibrated on held-out
queries for the chosen model and prompt.

Malformed artifacts fail closed. The loader rejects duplicate JSON keys, non-finite
values and inputs over 1 MiB. Query, variant, chunk and answer budgets bound runtime
and report size. Reports contain hashed query and benchmark identities, metrics,
stable finding codes and a canonical evidence digest; they do not reproduce question
or answer text.

## CLI

```bash
python -m src.context_order_audit context-order-runs.json \
  --output context-order-report.json
```

Exit codes are `0` for accepted evidence, `3` for a well-formed policy rejection and
`2` for malformed input. Output files are written atomically.

The benchmark artifact uses schema version 1:

```json
{
  "schema_version": 1,
  "benchmark_id": "release-17",
  "model_id": "local-model-v3",
  "prompt_template_id": "grounded-answer-v2",
  "retrieval_snapshot_digest": "<sha256>",
  "generation_config_digest": "<sha256>",
  "generated_at": "2026-09-25T23:00:00+00:00",
  "queries": [
    {
      "query_id": "auth-1",
      "chunk_ids": ["a", "b", "c", "d"],
      "variants": [
        {
          "variant_id": "baseline",
          "baseline": true,
          "ordered_chunk_ids": ["a", "b", "c", "d"],
          "cited_chunk_ids": ["a", "c"],
          "answer": "A generated answer.",
          "insufficient_evidence": false
        }
      ]
    }
  ]
}
```

## Limitations

Lexical stability is not semantic equivalence, factual correctness or entailment. A
consistently wrong answer can pass, while a valid paraphrase can reduce token
Jaccard. Citation-set stability does not prove that citations support the claims.
This gate therefore complements retrieval, citation, grounding and human-review
checks already present in the repository.

The producer is trusted to hold all non-order variables fixed. Production evidence
should be generated by a versioned benchmark runner, stored immutably and signed.
For stochastic models, run multiple seeds and estimate uncertainty instead of
treating a single set of permutations as a universal reliability claim.
